# Передача сесії — 100 ГРАМ

Нотатка для наступної Claude-сесії (або для себе), що саме лишилось
незакінченим після попередньої сесії. Гілка: `claude/telegram-100-gram-clone-fuadhq`.

## Що зроблено в цій сесії (ще не перевірено живим користувачем)

Користувач попросив "роби все, що не потребує мене особисто і грошей" —
нижче список того, що було реалізовано автономно, без змін `firestore.rules`
(щоб не вимагати ручної публікації в Firebase Console) і без зовнішніх
платних сервісів:

1. **Виправлено реальний баг**: `subscribeMessages` раніше брав
   `orderBy("createdAt", "asc") + limit(200)` — це фіксувало живе вікно на
   перші 200 повідомлень чату НАЗАВЖДИ; будь-що надіслане після 200-го
   повідомлення в чат ніколи не з'являлось у живому перегляді. Виправлено на
   `desc + limit(50)` + реверс, додано `loadOlderMessages()` і кнопку
   «⬆ Завантажити старіші» в `ChatWindow.tsx` для підвантаження історії без
   live-слухача на неї. Автоскрол донизу тепер прив'язаний лише до
   live-вікна, щоб підвантаження старих повідомлень не смикало скрол.
2. **Відновлення пароля**: `requestPasswordReset()` в `firestore-api.ts`
   (обгортка над `sendPasswordResetEmail`, ковтає `auth/user-not-found` щоб
   не давати enumeration), проведено через `AuthContext`, UI — перемикач
   «Забули пароль?» на `Login.tsx` (не окрема сторінка/роут).
3. **ErrorBoundary** (`components/ErrorBoundary.tsx`), обгортає `<App/>` в
   `main.tsx` — рендер-креш більше не дає білий екран, показує екран
   "Перезавантажити".
4. Прибрано мертве поле `ChatMessage.editedAt` (було в типі, ніде не
   писалось і не читалось — функції редагування повідомлень немає).
5. Ліміт довжини повідомлення `MAX_MESSAGE_LENGTH = 4000` в `constants.ts`,
   enforced і через `maxLength` на textarea, і валідацією при сабміті в
   `MessageInput.tsx`.
6. **ESLint** додано (`eslint.config.js`, flat config). Свідомо НЕ
   увімкнено `eslint-plugin-react-hooks` v7 full `recommended` preset —
   він тягне нові React Compiler-правила (`set-state-in-effect`, `refs`,
   `purity`, ...), які зафлагують як помилки типові, усталені React 18
   патерни, що вже є по всьому коду (напр. `setLoading(true)` на початку
   data-fetching ефекту). Залишено лише класичні `rules-of-hooks` +
   `exhaustive-deps`. `npm run lint` — 0 помилок, одне очікуване
   попередження (fast-refresh на `AuthContext.tsx`, бо там в одному файлі
   і компонент `AuthProvider`, і хук `useAuth` — звичайний і прийнятний
   патерн, не варто розносити по файлах).
7. **Vitest** додано (`vitest@^2`, сумісна з `vite@^5` — новіші vitest 3.x
   вимагають vite 6+, апгрейдити vite не стали, це окреме рішення з
   наслідками). `normalizeUsername` в `firestore-api.ts` тепер
   `export`-нута заради тестованості. Тести: `constants.test.ts`
   (`isSiteAdmin`), `data/firestore-api.test.ts` (`normalizeUsername`).
   `npm run test` — усі проходять. **Це не повне покриття** — Firestore
   security rules, транзакції гаманця, права доступу в чатах і далі не
   протестовані автоматично (вимагало б Firebase emulator suite — окрема,
   більша робота, не зроблено).
8. **GitHub Actions CI** (`.github/workflows/ci.yml`): на кожен push і PR
   запускає `npm ci && npm run lint && npm run test && npm run build` у
   `frontend/`. Ще не бачила жодного реального запуску (локально не
   перевірити GitHub Actions) — варто глянути на вкладці Actions після
   першого пушу, чи все зелене.
9. README.md оновлено під це (нові фічі, нова структура файлів, секція
   про вікно повідомлень/пагінацію, команди lint/test у "як перевірити
   стан").

**Відоме, свідомо не чіпали:**
- `npm audit` показує 8-11 вразливостей (критична — у `vitest` через
  `--ui` dev-сервер, якого проєкт не використовує; решта — у
  `@grpc/grpc-js` (транзитивна через `firebase`), `esbuild`/`vite`,
  `react-router`). Усі фікси вимагають `--force` і мажорних апгрейдів
  (`firebase@9` — даунгрейд!, `vite@8`, `react-router-dom@7`) — свідомо не
  робили автономно, це ризиковано без живого тестування проти Firebase.
  Якщо матимеш час і можливість протестувати на реальному акаунті — варто
  розглянути окремо, по одному пакету.
- Rate-limiting на відправку повідомлень на рівні `firestore.rules` не
  додавали (вимагало б публікації правил користувачем вручну).
- Push-сповіщення (FCM), Sentry/моніторинг помилок, audit-log дій адміна —
  не робили: або вимагають зовнішнього акаунта користувача, або (audit-log)
  вимагають зміни `firestore.rules`.

**Перше, що варто зробити в новій сесії:** переконатись, що
`npm run lint && npm run test && npx tsc -b && npx vite build` з
`frontend/` все ще проходять чисто (могло розійтись, якщо хтось правив код
руками між сесіями), і що GitHub Actions реально зелений після пушу.

## Свідомі архітектурні рішення (не пропонуй їх "виправити")

- **Без Firebase Storage.** Користувач відмовився від плану Blaze
  (вимагає прив'язки картки). Фото аватарок і повідомлень стискаються
  на клієнті через `frontend/src/utils/image.ts` (canvas → JPEG data URL)
  і зберігаються прямо в полі Firestore-документа. Аватарки: ліміт
  ~250КБ (бо дублюються в `memberProfiles` кожного спільного чату).
  Фото повідомлень: ліміт ~700КБ (кожне повідомлення — окремий документ,
  без дублювання).
- **Без ботів.** Користувач явно відмовився через вимогу Cloud
  Functions/Blaze плану.
- **GIF тільки за посиланням**, не завантаженням файлу — свідомий вибір
  користувача (щоб не втрачати анімацію при стисканні і не мати
  проблем з розміром).
- **Один хардкоджений сайт-адмін** — `SITE_ADMIN_USERNAME` в
  `frontend/src/constants.ts`, і той самий рядок в `firestore.rules`
  (`isSiteAdmin()`). Не self-settable, ніхто не може видати собі ці права
  через devtools. Якщо треба більше адмінів — це вимагатиме зміни на
  список імен в обох місцях.
- **ГРАМи редагуються клієнтом напряму** (`users/{uid}.grams`) — реальна
  server-side цілісність вимагала б Cloud Functions на платному плані.
  Прийнятний компроміс для ігрової валюти; не зберігати тут нічого
  цінного.
- **`eslint-plugin-react-hooks` навмисно обмежено** двома класичними
  правилами (`rules-of-hooks`, `exhaustive-deps`) замість повного v7
  `recommended` preset — див. пункт 6 вище. Не вмикай повний preset без
  окремої домовленості — це призведе до купи нових "помилок" на звичному,
  робочому коді.

## Правила Firestore — ручна публікація, не автодеплой

`firestore.rules` у репозиторії — це джерело правди, але Firebase **не
підхоплює його автоматично**. Кожна зміна файлу вимагає, щоб користувач
вручну скопіював вміст у Firebase Console → Firestore Database → Rules →
Publish. Поточна версія в репозиторії (з `exists()`-перевірками в
`isSiteAdmin()`/`isGloballyMuted()`) **підтверджена опублікованою**
користувачем раніше, і **цю сесію `firestore.rules` не змінювали взагалі**
(свідомо, щоб не вимагати від користувача дій).

Те саме стосується `storage.rules` — **але цей файл видалено**, бо
Storage вимагає план Blaze, від якого відмовились (дивись коміт
`c6e8cdf "Прибрати завантаження фото аватарки"`).

## Дрібне, ще не зроблене (опційно, не блокує нічого)

- В [репозиторії Аксіоми](https://github.com/Ivanko-del/Aksioma)
  (окремий проєкт користувача, у мене лише read-доступ) є мапа
  `PARTNER_NAMES` в `app.js` — можна додати запис для "100gram", щоб
  назва красиво відображалась у самій Аксіомі. Користувач має зробити
  це сам у своєму репозиторії.
- Push-сповіщення (FCM) — не реалізовано, вимагає Firebase Console
  конфігурації (VAPID-ключ) і тестування на реальному пристрої.
- Моніторинг помилок на проді (Sentry чи аналог) — не підключено,
  вимагає акаунта користувача.

## Як перевірити стан проєкту швидко

```bash
cd frontend
npm run lint      # ESLint
npm run test      # Vitest
npx tsc -b        # типи мають бути чисті
npx vite build    # білд має проходити без помилок
```

Живе тестування Firebase з цього sandbox не працює (мережевий проксі
блокує auth/firestore ендпоінти) — весь QA цієї сесії йшов через
статичний аналіз (lint/build/unit-тести), без живого Firebase. Реальну
перевірку (чи справді відновлення пароля шле листа, чи справді чат з
200+ повідомлень тепер оновлюється) має зробити користувач на
задеплоєному сайті.
